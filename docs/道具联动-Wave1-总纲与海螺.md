## 0. 实读核对：与交底基线的三处出入（先读，影响整个方案）

主理人给出的基线**大体属实**（18 处 `reward` 已接线、`useItem`/`requireItem` 各仅 1 处且都是 `powerbank`、掉落 8 件 / 商店 6 件在 story.json 零引用），但实读中发现**三条断链**，它们决定了本方案能不能真的跑起来。

### 出入一（P0 · 阻断级）：`requireItem` 现在是死代码，永远不会放行

`js/event-render.js` 第 221 行与第 231 行：

```js
if (choice.requireItem && !(gameState.inventory && gameState.inventory[choice.requireItem] > 0)) return;
```

而 `js/backpack.js:180` 里道具存进背包的形态是**对象**：

```js
inv[itemId] = { icon: item.icon, count: 0, description: item.desc, quote: '' };
```

`对象 > 0` 在脚本里先转字符串再转数字，得到非数字，比较结果恒为假 —— 于是 `!false...` 整个判断恒真，**带 `requireItem` 的选项永远被 return 掉**。这意味着现在唯一那条已接线的伏笔（`没电的窘境`·A 拿出充电宝）**玩家一辈子也看不到**。

同文件第 18 行的写法才是对的，可直接照抄：

```js
const owned = Object.keys(inv).filter(k => inv[k] && inv[k].count > 0);
```

**结论：本稿「伏笔回收」这一整类（也是用户想要的核心体验）依赖程基岩改这两行。** 建议修正为：

```js
if (choice.requireItem && !(gameState.inventory
    && gameState.inventory[choice.requireItem]
    && gameState.inventory[choice.requireItem].count > 0)) return;
```

> 顺带说明：这条 bug 也解释了为什么"道具拿到手就成死物"—— 不只是没写文案，是**写了也不会显示**。

### 出入二（P0 · 阻断级）：两套背包用两种键，掉落物与商店货无法被 `requireItem` 命中

- `js/backpack.js:179` 用 **英文 id** 作键：`inventory['shell']`
- `js/inventory.js:66` 的 `addToInventory(name, ...)` 用 **中文名** 作键：`inventory['精致贝壳']`

`gift.js:24` 与 `shop.js:95` 走的都是后者。所以就算修好了出入一，`requireItem: "shell"` 依然打不中随机掉落来的那枚贝壳 —— 它躺在 `inventory['精致贝壳']` 里。

**结论：海螺要能被剧情引用，必须从「随机掉落」升格为「剧情信物」**（登记进 `ITEMS`，走 `reward` 发放）。这不是绕路，这恰恰是用户那句"闲置在那里很不好"的**根因**：它从一开始就被放错了系统。

### 出入三（P1 · 功能死链）：商店 6 件货的"赠予"入口早就断了

`js/event-render.js:3` 的 `injectItemChoices()` 本来是个现成的"赠予共鸣"引擎 —— 背包里有礼物，事件里就自动多一个"送出"按钮。但它的 `itemMap` 与第 22 行的反查表用的是 `js/shop.js:1` 那个**旧的 `gifts` 数组**（红玫瑰 / 手工巧克力 / 淡雅香水 / 纯银项链 / 大白熊公仔 / 情侣手表 / 游乐园门票 / 拍立得），而玩家实际能买到的是 `renderShopList()` 内的 `shopGifts`（奶茶 / 永生玫瑰 / 毛绒玩偶 / 精美项链 / 香薰蜡烛 / 定制礼物）。

**两组名称一个都对不上**（"永生玫瑰"≠"红玫瑰"，"精美项链"≠"纯银项链"，"毛绒玩偶"≠"大白熊公仔"），`giftByName[itemName]` 恒为 `undefined` → `return` → 按钮从未出现过。

**结论：商店 6 件货不需要写一句 story.json，只要把 `gifts` / `itemMap` 对齐到 `shopGifts` 的 6 个名字，"赠予共鸣"当场复活。** 这是本轮性价比最高的一处修复。

## 1. 三条设计红线（本稿自我约束，请审核时一并检查）

1. **门控只做加法，不做减法。** 所有 `requireItem` 选项一律是该事件的**第 5 / 第 6 个额外选项**，原有 A–D 一个不动。没道具的玩家看到的是完整的原事件，不会觉得"我少了点什么"；有道具的玩家多一条只属于他的路。
2. **持有道具不得成为主导策略。** 每个新增门控选项的 `like`/`heart` **不高于该事件现有最优选项**。伏笔的奖赏是"被认出来了"这件事本身，不是数值。下表每一条都标了对照值。
3. **同一种巧思全稿只用一次。** 古注体、书信体、跨周目回响、结局尾声判定 —— 这四样各只出现在海螺四版中的一版里，选定其一后，其余三种写法在全作范围内作废，不得复用到别的道具上。

## 1.2 主表：系统 B · 随机掉落（8 件，25% 概率，`gift.js:5-14`）

**先讲一个必须先说清的设计问题。** 随机掉落物**不适合做 `requireItem` 门控**：25% 概率、每局最多掉一件、掉哪件还是随机 —— 玩家会遇到"上一局有这个选项，这一局没有"的薛定谔体验，既解释不通，也无法复现。这是认知过载的典型来源，属于设计红线。

所以掉落物的正确出路只有两条：
- **结局信物**：`showResult()` 尾声读背包，有就多一句，没有就没有。玩家永远不会觉得"我错过了什么"，因为他压根不知道有这句 —— 这是掉落物唯一合适的联动形态。
- **诚实剔除**：保持纯数值，但把那句通用模板文案改掉。

## 1.6 与「每事件最多 1 个背包道具」原则的冲突检查

现行基线原则原文：**每事件最多 1 个 `reward`；`choice.photo` 不占背包格，可与 1 个 reward 共存。**

逐条核对本稿：

| 检查项 | 结果 |
|---|---|
| 本稿是否新增 `reward`？ | **仅 1 处**（海螺），且落在当前 `reward` 数为 0 的事件上 —— 雾天线放在「雾中迷路」（该事件无 reward），台风线放在「雨过天晴」（该事件无 reward）。✅ 不违例 |

| 是否有事件被塞入 2 个回收点？ | **无**。1.1~1.3 表中每个事件名只出现一次。✅ |
| 新增选项是否挤爆选项数？ | 最多的是 `sunny / 看夕阳`（A–E 五项 → 加 F 六项）与 `cloudy / 看夕阳`（同）。`sunny / 公园野餐` 已有 A–F 六项的先例，六项在现有 UI 下可接受。✅ 但**不建议任何事件超过 6 项**，本稿最大即 6 |

# 第二部分 · 海螺专项 · 4 版完整剧情

## 2.0 动笔前必须讲清的一件事：两个创意不在同一个周目里

用户说"灵活一点，可以把两个创意串成一条暗线"。我很想这么做 —— 但实读 `meta.weatherGroups` 后必须诚实汇报：**串不起来。**

```
"weatherGroups": { "晴天":["sunny","sunny2"], "多云":["cloudy","cloudy2"],
                   "雨天":["rainy","rainy2"], "雪天":["snowy"] }
```

`cloudy2`（雾天）属于**多云**，`rainy2`（台风天）属于**雨天**。玩家开局只选一种天气，`StoryLoader.pickWeather()` 在该天气的变体里随机抽一条线跑到底。所以：

> **一个周目里，玩家要么在雾天，要么在台风天，永远不可能两者都经历。**
> "雾天海滨公园捡到海螺 → 当晚台风把它送回来"这条链，在单周目内在物理上不成立。

这不是坏消息，它反而指出了三条各有味道的出路：

| 出路 | 做法 | 代价 |
|---|---|---|
| **甲：各自闭环** | 雾天线自己捡自己收；台风线自己捡自己收。两条线互不知道对方存在 | 零工程风险，但放弃了"暗线"的浪漫 |
| **乙：跨周目回响** | 用已有的 `localStorage['collected-items']`（`backpack.js:161` 已在写）判定"你上辈子捡过海螺" | 需引擎新增一个 `requireCollected` 字段（约 6 行） |
| **丙：结局尾声** | 不在事件里回收，改在 `showResult()` 尾声读背包补一段 | 需改 `js/result.js`，且好结局有 9 个评价分支要兼容 |

四个版本就是这三条出路的不同组合。**另外三件必须先定的事：**

1. **海螺必须从随机掉落池升格为剧情信物。** 出入二已经证明，`gift.js` 掉落的贝壳躺在 `inventory['精致贝壳']`（中文键），而 `requireItem` 查的是 `inventory['shell']`（英文键）—— 剧情永远够不着它。四个版本**全部**以此为前提。
   - `js/gift.js:9` 的 `shell` 条目从 `randomGifts` 数组中**移除**（掉落池 8 件 → 7 件）；
   - `js/backpack.js` 的 `ITEMS` 中**新增登记**：

   ```js
   shell: {
     id: 'shell', name: '海螺', icon: '🐚',
     color: '#38bdf8', bg: 'linear-gradient(135deg,#38bdf8,#a5f3fc)',
     desc: '（按选定版本填写，四版各有一句，见下）'
   }
   ```

2. **名字要不要从"精致贝壳"改成"海螺"？** 用户口语一直说"海螺"，而代码里叫"精致贝壳"。贝壳是扁的，海螺是能贴到耳朵上听声音的 —— **本方案全部四版的核心动作都是"贴到耳朵上"，所以必须叫海螺。** 建议 `name` 定为「海螺」，`icon` 用 🐚。这是**开放问题 1**，请用户拍板。

3. **创意乙的实现路径，我选 (a)。** 理由三条：
   - `js/endings.js` 里只有 `showBadEnd`（失败）与 `showMoodEnd`（惹毛她），把海螺塞进失败结局语义完全错位；真正的好结局是 `js/result.js` 的 `showResult()`。
   - 「无事发生的温柔」是台风线**最后一个事件**（idx12），玩家做完这个选择就直接进 `showResult()`。**它在体感上已经就是结局前一刻**，仪式感损失极小。
   - 纯 `story.json` 改动可被 `tools/test-flow-static.mjs` 静态校验兜住，而改 `result.js` 要兼容 9 个评价分支（灵魂契约 / 心动频率 / 豪门盛宴 / 钢铁直男……），回归面大得多。
   - **例外：版本四**故意走 (b)，作为"愿景版"供对比。

## 版本四 · 《回声》

### 1 · 声口定位
**实验性 · 跨周目回响 + 第二人称结局尾声。** 这一版的特殊形式是：**海螺会记得你上一个周目**。全稿唯一一次让道具穿透单局边界；并且唯一一次把回收放在 `showResult()` 的结局尾声里，用第二人称直接对玩家说话。选定此版后，"跨周目回响"与"结局尾声判定"这两种巧思在全作范围内作废（红线 3）。与前三版的区别：**它是唯一真正实现了用户"串成一条暗线"设想的方案** —— 代价是要动引擎。
> 对应创意：**创意甲 + 创意乙串成一条暗线**，采用实现路径 **(b)**。

### 2 · 获取链路

获取点与版本三完全一致（雾天「雾中迷路」·E + 台风天「雨过天晴」·F，文案沿用版本三或版本一/二任选，本版不重复抄录）。**本版的全部创新在回收侧。**

### 3 · 完整文案：三段结局尾声

引擎读取 `localStorage['collected-items']`（`backpack.js:157` 的 `getCollectedItems()` 已经写好，只需导出）与本局 `gameState.inventory['shell']`，按下表三选一，追加到 `showResult()` 的 `result-highlight` 之后。

| 判定 | 条件 | 尾声文案 |
|---|---|---|
| **甲 · 初遇** | 本局持有海螺 **且** 跨周目记录里此前没有 | 「回家路上你把海螺又举到耳边。它当然什么都没有，只是一段被磨圆的碳酸钙，把你自己的血流声还给你。可你还是听了很久——因为今天她也这样听过。」 |
| **乙 · 回响** | 本局持有海螺 **且** 跨周目记录里已经有过 | 「你把海螺举到耳边。奇怪的是，这次听见的不太一样：像是很多个不同天气的下午叠在一起，有雾里的水声，有台风过境后滴水的屋檐，还有某一次你已经想不起是哪一天的、她笑出声的半秒。你想，原来这东西不是用来听海的。」 |
| **丙 · 缺席** | 本局未持有海螺，但跨周目记录里有过 | 「今天没有捡到什么。回家翻抽屉的时候，你摸到一枚旧海螺——上一次，是在另一种天气里捡到的。你把它举到耳边，什么也没听见。你想，大概是因为她今天没有把耳朵凑过来。」 |

- 三段都是**第二人称、回家路上、无对白**，与游戏正文（现场、有对白）形成时态与人称的双重错位 —— 这就是它"实验性"的所在。
- 若本局与跨周目都没有海螺，**什么也不追加**，玩家零感知。

### 4 · 字段绑定与引擎改动

**story.json 侧**：与版本三相同（两个 `reward: "shell"` 获取点，数值同版本三）。

**引擎侧（这是本版的代价，请程基岩评估）**：

1. `js/backpack.js` —— 导出已有的跨周目查询（约 1 行）：
   ```js
   window.hasCollected = function (id) { return getCollectedItems().has(id); };
   ```
2. `js/result.js` —— 在 `document.getElementById('result-highlight').textContent = '💡 ' + highlight;` 之后插入约 12 行：
   ```js
   // 海螺 · 结局尾声回响
   var hasNow = !!(gameState.inventory && gameState.inventory['shell']
                   && gameState.inventory['shell'].count > 0);
   var hasEver = (typeof hasCollected === 'function') && hasCollected('shell');
   var echo = '';
   if (hasNow && !hasEver) echo = '（甲·初遇文案）';
   else if (hasNow && hasEver) echo = '（乙·回响文案）';
   else if (!hasNow && hasEver) echo = '（丙·缺席文案）';
   if (echo) { /* 追加一个 <div class="ending-echo"> 到 .end-wrap */ }
   ```
3. **时序陷阱（必须提醒工程）**：`backpack.js:185` 的 `addCollectedItem(itemId)` 是在 `acquireItem` 里**当场**写入 localStorage 的。所以玩家本局刚捡到海螺，`hasCollected('shell')` **立刻**就为真 —— 判定甲永远打不中，会全部落到乙。
   **修复方案**：`getCollectedItems()` 在**开局时**（`resetBackpack()` 里）快照一份到 `gameState.collectedAtStart`，结局尾声用快照判定，而不是用实时值。这是本版最容易踩的坑，也是它工程量大于前三版的主要原因。

## 2.6 我的推荐

### 推荐：**版本三《螺纹考》为主体，版本四的结局尾声留作 Wave 2 的可选升级。**

理由四条：

1. **只有版本三同时兑现了用户的两个创意，且不欠工程债。** 版本一、二各砍掉一半需求；版本四虽然最动人，但它要改 `result.js` —— 那个函数里有 9 个评价分支和一堆 DOM 操作，在"用户在线等审核"的节奏下不该同时开这个口子。

2. **"灵活一点"在版本三里的落点，是让两条线各自成立而非硬串。** 我原本也想做暗线，直到实读 `weatherGroups` 发现雾天与台风天不同属一种天气、单周目互斥。硬串就得改引擎；而版本三的做法是——**同一枚海螺，两种来路，两种听法**。雾天那枚是"你们走错路才遇见的"，台风那枚是"风替你搬来的"，注疏体那两句「所致者不在物，在其来路」正是在讲这件事。这比强行串成一条时间线更贴合作品本身的气质。

3. **注疏体只用一次，用在这里最值。** 全库 32 件道具里，海螺是唯一一件"物理上会发声、但发的其实是你自己的声音"的东西 —— 这个悖论配得上一段伪注疏。若把注疏体浪费在古风折扇或古董小镜上（它们看起来更"古"），反倒是买椟还珠。

4. **版本四不是废案，是路线图。** 它的三段尾声文案可以原样保留，等 Wave 2 引擎有余力时再接上。届时版本三的两个事件内回收点作为"过程回响"，版本四的结局尾声作为"终局回响"，正好是两层。

## 2.7 需要用户拍板的开放问题（3 条）

1. **道具名定「海螺」还是保留「精致贝壳」？** 本方案四版的核心动作都是"贴到耳朵上听"，贝壳（扁的）做不到，海螺（螺旋腔）才行。**建议改名为「海螺」，icon 用 🐚。** 若坚持保留原名，四版的动作描写需整体重写为"贴在耳边试"这类弱化表述，味道会掉一档。
